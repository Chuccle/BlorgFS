# BlorgFS

Kernel-mode Windows filesystem driver that presents an HTTP backend as a
mounted, read-only volume (`B:`). Built on async WSK networking, an optional
hand-rolled TLS 1.3 client, and a keep-alive connection pool.

## Repository layout

```
src/           the driver, and only the driver -- one .vcxproj, its INF,
               and the sources that compile into BlorgFS.sys
tests/         everything that verifies it
  sandbox/       usermode targets that compile the real driver sources
                 against a kernel model, plus the systematic scheduler
                 and the CBMC harnesses under verification/
  TlsTest/       RFC 8448 vectors        TlsFuzzTest/  record layer under ASan
  TlsHandshakeTest/  live openssl handshake
  PerfHarness/   workload driver and counter reader
  VolumeTester/  volume-level behaviour against a mounted drive
tools/         tiered check runner, metric comparison, crash triage,
               differential correctness harness
deploy/        VM deploy pipeline (see AGENTS.md)
third_party/   submodules: flatcc, picohttpparser, schemas, googletest,
               and server-rs (the backend this driver ships with)
VERSION        the combined package version (see "Packaging" below)
```

## Building and testing

Run the tiered check script rather than a hand-rolled build:

```bash
powershell -File tools/Invoke-BlorgChecks.ps1 -Tier Fast
```

| Tier | What it does | Needs |
|---|---|---|
| `Build` | Compile + link everything with PREfast | nothing |
| `Fast` (default) | Build, plus RFC 8448 crypto vectors and the fuzz corpus | nothing |
| `Perf` | Fast, plus PerfHarness workloads compared against a stored baseline | driver loaded, backend reachable |
| `All` | every tier | as above |

Exit code is 0 only if everything in the tier passed. Run `-Tier Fast` before
calling any change done — cheaper tiers don't run the crypto tests that catch
a `Tls.c` regression.

Three GitHub Actions workflows cover the rest: `build.yml` gates every push
and PR to `master` at the Fast tier, `verify.yml` runs CBMC proofs and
extended fuzz/interleaving coverage nightly, and `codeql.yml` runs weekly
(and on PRs touching its own config) with the pinned Microsoft driver query
packs.

## Packaging

BlorgFS ships together with its backend,
[server-rs](https://github.com/Chuccle/server-rs), pinned as the
`third_party/server-rs` submodule. The two repositories stay separate; this
one is the package root. They agree on the wire only because both compile
the same FlatBuffers schema from `Chuccle/schemas`, so
`tools/Test-BlorgPackagePins.ps1` fails if this repo's `third_party/schemas`
and the `schemas` submodule inside the pinned server-rs commit differ.
Dependabot bumps the two submodules together in one PR (`package-contract`
in `.github/dependabot.yml`), so a schema change arrives as a matching pair.

A package looks like this:

```
manifest.json   version; blorgfs, server_rs and schemas commits;
                signer thumbprint; SHA-256 of every file
driver/         BlorgFS.sys, BlorgFS.inf, BlorgFS.cat, BlorgFS.cer,
                Install-BlorgFS.ps1, Uninstall-BlorgFS.ps1
server/         linux-x64/server-rs        static (musl); where the backend runs
                windows-x64/server-rs.exe  single-machine fallback
```

`driver\Install-BlorgFS.ps1` runs as is from the unpacked package. Test
against the Linux server: the Windows one runs on loopback beside the driver,
on a case-insensitive filesystem, which hides how a real deployment behaves.

`VERSION` holds the package version. Untagged builds append both commits as
build metadata (`0.1.0+g417fc40.s2fa2955`: BlorgFS, then server-rs). A `v*`
tag must equal `v` + `VERSION`, and publishes the zipped package as a GitHub
release. Signing uses the WDK test certificate generated by the build, so
the driver only installs where test-signing is on, which
`Install-BlorgFS.ps1` turns on.

### Building a package in CI

`build.yml` builds the package on every push and PR, and uploads it as the
artifact `blorg-package-windows-x64`. Only the driver job runs on Windows,
because it needs MSVC, the WDK, signing and the usermode test suites. The
pins check, both server builds and the packaging step run on Linux.

To build a package of any branch or tag on demand, run the workflow from the
Actions tab ("Run workflow"), or through the API:

```bash
gh workflow run build.yml --ref <branch-or-tag> -f correlation_id=<any-id>
gh run list --workflow build.yml --event workflow_dispatch   # find the run by its name
gh run download <run-id> -n blorg-package-windows-x64
chmod +x server/linux-x64/server-rs   # artifact zips drop the executable bit
```

The run is named `Build BlorgFS <ref> <correlation_id>`, so a script that
starts runs can tell its own apart. server-rs always comes from the pin on
that ref; there is no way to build against another server commit except by
moving the pin.

### Building a package by hand

The same scripts CI runs, in the same order. Steps 1, 2 and 4 run anywhere
PowerShell 7 does. Step 3 needs Windows with Visual Studio and the WDK.

1. Check the pins: `pwsh tools/Test-BlorgPackagePins.ps1`.
2. Build the servers. This needs Rust, CMake and a C++ compiler for flatc,
   plus `musl-tools` for the Linux target and `gcc-mingw-w64-x86-64` for the
   Windows one when cross-building from Linux. On Windows, build with
   `-Target x86_64-pc-windows-msvc` instead.

   ```powershell
   ./tools/Build-BlorgServer.ps1 -Target x86_64-unknown-linux-musl -OutDir out/server/linux-x64
   ./tools/Build-BlorgServer.ps1 -Target x86_64-pc-windows-gnu    -OutDir out/server/windows-x64
   ```
3. Build and check the driver:
   `msbuild BlorgFS.sln /p:Configuration=Release /p:Platform=x64`, then
   `./tools/Test-BlorgDriverSignature.ps1 -BuildDir x64/Release`.
4. Assemble: `./tools/New-BlorgPackage.ps1 -ServerDir out/server -OutDir out/package`.

`Build-BlorgServer.ps1` builds flatc from server-rs's own
`buildtools/flatbuffers`, because the generated code must match server-rs's
flatbuffers crate. It then runs `cargo build --release --locked`. Don't copy
these steps into another build; call the scripts or dispatch `build.yml`, so
every package is built the same way.

## Deploying to a VM

BlorgFS is a kernel driver, so it's developed and tested against a throwaway
Windows VM rather than the build machine. Copy `deploy/blorgfs.env.example`
to `deploy/blorgfs.env` and fill it in once; after that, deploying takes no
arguments:

```powershell
.\deploy\Deploy-ToVM.ps1 -Configuration Release
```

For benchmarking, use `-ForBenchmark` instead, which deploys Release, clears
Driver Verifier, and waits for the guest to go idle before reporting success.
